## 2) Data Model and Schema Changes (#3)

### 2.1 Interview Entity

Defined in [backend/app/models/Interview.java](backend/app/models/Interview.java).

Key fields:

- `id` (PK)
- `rajobApplication` (FK to `rajob_application.id`)
- `createdBy` (FK to `user.id`)
- `proposedTimes` (JSON serialized as `String`)
- `chosenTime`
- `status` (`proposed`, `scheduled`, `completed`, `cancelled`)
- `createdTime`, `updatedTime`
- `location`, `notes`

### 2.2 Evolution Script

Defined in [backend/conf/evolutions/default/2.sql](backend/conf/evolutions/default/2.sql).

Creates table `interview` with:

- FK `rajob_application_id` -> `rajob_application(id)` (cascade delete)
- FK `created_by_user_id` -> `user(id)` (set null on delete)
- indexes on `rajob_application_id`, `created_by_user_id`, `status`

Down migration drops `interview` table.

## 3) Endpoints and Route Surface

> Note: the backend interview controller endpoints for creating and fetching interviews have now been fully implemented and integrated with the frontend routes.

### 3.1 Implemented Scheduling Routes (Backend & Frontend)

From [backend/conf/routes](backend/conf/routes):

- `POST /rajob/interview/schedule` -> `RAJobController.scheduleInterview()`
- `GET /rajob/interview/job/:jobId` -> `RAJobController.getScheduledInterviews(jobId)`

From [frontend/conf/routes](frontend/conf/routes):

- `GET /rajob/schedule/:jobId` -> `RAJobController.raInterviewSchedulePage(jobId)`
- `POST /rajob/schedule/:jobId` -> `RAJobController.scheduleInterviewPOST(jobId)`
- `POST /rajob/reschedule/:id` -> `RAJobController.rescheduleInterviewPOST(id)`
- `POST /rajob/cancel/:id` -> `RAJobController.cancelInterviewPOST(id)`

Controller methods are in [frontend/app/controllers/RAJobController.java](frontend/app/controllers/RAJobController.java).

### 3.2 Request/Response Examples (implemented)

#### A) Create schedule proposal

Request:

- Method: `POST`
- URL: `/rajob/schedule/123`
- Form payload example:
  - `applicantId=55`
  - `date1=2026-05-01`
  - `time1=10:00 AM`
  - `date2=2026-05-02`
  - `time2=02:00 PM`

Response (current behavior):

- HTTP: `303` redirect (Play redirect) to `/rajob/schedule/123`
- flash: success response (or error if validation fails)
- **Backend action:** Posts payload to `/rajob/interview/schedule` and creates an `Interview` DB record with `status` = `"interview_proposed"`.

#### B) View scheduled/proposed list (faculty page)

Request:

- Method: `GET`
- URL: `/rajob/schedule/123`

Response (current behavior):

- HTTP: `200`
- content: HTML page rendering [frontend/app/views/raInterviewSchedule.scala.html](frontend/app/views/raInterviewSchedule.scala.html)
- includes two tabs:
  - `Applicants`
  - `Scheduled Interviews` (Dynamic data fetched from backend DB!)

#### C) Reschedule interview

Request:

- Method: `POST`
- URL: `/rajob/reschedule/101`

Response (current behavior):

- HTTP: `200`
- body: `Rescheduled` (Action uses mock response pending backend `PATCH` route implementation)

#### D) Cancel interview

Request:

- Method: `POST`
- URL: `/rajob/cancel/101`

Response (current behavior):

- HTTP: `200`
- body: `Cancelled` (Action uses mock response pending backend `PATCH` route implementation)

## 4) Authorization Rules

### Expected (per feature requirement)

- Faculty only (`userType == 1`) for create/reschedule/cancel.
- Faculty must own the related RA job/application.
- Return `401` for unauthenticated requests.
- Return `403` for authenticated but unauthorized users.

### Current implementation status

- `checkLoginStatus()` is active and enforced in `raInterviewSchedulePage()` and `scheduleInterviewPOST()`.
- Ownership checks are still pending in the UI actions.

## 5) Frontend Flow and Validation (#4)

Implemented page: [frontend/app/views/raInterviewSchedule.scala.html](frontend/app/views/raInterviewSchedule.scala.html)

### 5.1 User Flow

1. Faculty opens schedule page by job id.
2. In `Applicants`, click `Schedule`.
3. Modal opens with 3 candidate slots.
4. Submit schedule proposal.
5. In `Scheduled Interviews`, faculty can click `Reschedule` or `Cancel`.

### 5.2 Validation Behavior (current)

- UI enforces:
  - Slot 1 required (`date1`, `time1` required fields).
  - Slots 2/3 optional.
- Server-side validation:
  - Prevents dates scheduled in the past.
  - Validates presence of `applicantId`.

## 7) Error Scenarios

### 7.1 Invalid slot input

- Current UI blocks empty Slot 1 via HTML required fields.
- Missing server-side validation: invalid combinations can bypass with crafted requests.
- Target behavior: return `400` with field-level error message.

### 7.2 Unauthorized faculty / unauthenticated access

- Current scheduling handlers do not enforce login/role checks.
- Target behavior:
  - `401` if not logged in
  - `403` if user is not faculty or not job owner

### 7.3 Invalid interview/application id

- `reschedule` and `cancel` currently return fixed text and do not validate id existence.
- Target behavior: return `404` for missing interview, `400` for malformed id.
